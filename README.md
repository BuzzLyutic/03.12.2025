# Link Checker Service

Веб-сервер для проверки доступности интернет-ресурсов.

## Возможности

- Проверка доступности одной или нескольких ссылок
- Генерация PDF-отчётов по ранее проверенным наборам ссылок
- Graceful shutdown с сохранением незавершённых задач
- Восстановление состояния после перезапуска

## Архитектура


### Используемые паттерны

1. **Clean Architecture** - Архитектурный подход, при котором код разделяется на независимые слои с чёткими границами. Зависимости направлены от внешних слоёв к внутренним - бизнес-логика не зависит от деталей реализации (БД, HTTP, PDF).

    **Почему выбран:**
    - Тестируемость - каждый слой можно тестировать изолированно
    - Гибкость - легко заменить хранилище (файл - БД) без изменения бизнес-логики
    - Читаемость - новый разработчик быстро понимает структуру
    - Соответствует требованию - простота без лишнего усложнения

2. **Repository Pattern** - Абстракция над механизмом хранения данных. Бизнес-логика работает с репозиторием через простой интерфейс, не зная деталей (файл, БД, память).

    **Почему выбран:**
    - Требование задания - без внешней БД, но с возможностью сохранения состояния
    - Расширяемость - легко перейти на PostgreSQL/Redis без изменения handler'ов
    - Инкапсуляция - вся работа с файлом в одном месте
    - Thread-safety - синхронизация скрыта внутри репозитория

3. **Graceful Shutdown** - Паттерн корректного завершения работы сервиса: перехват сигналов ОС, ожидание завершения активных операций, сохранение состояния перед остановкой.

    **Почему выбран:**
    - Требование задания - не терять задачи при перезапуске
    - Production-ready - стандартная практика для Go-сервисов
    - Надёжность - данные не теряются при Ctrl+C или kill

4. **Context Propagation** - Передача context.Context через все слои приложения для управления временем жизни операций: отмена, таймауты, дедлайны.

    **Почему выбран:**
    - Идиоматичный Go - стандартный подход в Go для управления горутинами
    - Отмена операций - если клиент отключился, не тратим ресурсы
    - Таймауты - защита от зависания на медленных ресурсах
    - Graceful shutdown - возможность отменить долгие операции при остановке

### Сценарий Graceful Shutdown

1. Получение сигнала SIGINT/SIGTERM
2. Маркировка сервера как "shutting down"
3. Новые запросы сохраняются как pending задачи
4. Ожидание завершения активных задач (с таймаутом)
5. Сохранение состояния в файл
6. Остановка HTTP сервера

При следующем запуске pending задачи автоматически обрабатываются.

## Установка и запуск

```bash
# Клонирование
```

## Конфигурация

### Через переменные окружения:


| Переменная | По умолчанию | Описание |
|------------|------------|------------|
| SERVER_ADDR | :8080 | Адрес сервера |
| READ_TIMEOUT | 15 | Таймаут чтения (сек) |
| WRITE_TIMEOUT | 15 | Таймаут записи (сек) |
| SHUTDOWN_TIMEOUT | 30 | Таймаут остановки (сек) |
| CHECK_TIMEOUT | 10 | Таймаут проверки ссылки (сек) |
| DATA_PATH | data/storage.json | Путь к файлу данных |


## API

### POST /check
Проверка доступности ссылок.

Запрос:

```JSON
{
  "links": ["google.com", "invalid-domain.xyz"]
}
```
Ответ:

```JSON

{
  "links": {
    "google.com": "available",
    "invalid-domain.xyz": "not available"
  },
  "links_num": 1
}
```

### POST /report
Получение PDF-отчёта.

Запрос:

```JSON

{
  "links_list": [1, 2]
}
```
Ответ: PDF файл

### GET /health
Проверка состояния сервиса.

Ответ:

```JSON

{
  "status": "ok"
}
```
